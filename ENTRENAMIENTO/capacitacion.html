01Lo primero: NO es ASP.NET MVC

Guía completa: 01-Guias/GUIA_01_PATRON_MVC.md

Si alguien llega con la idea de ASP.NET MVC (rutas, ActionResult, Razor), va a escribir código que no encaja con el resto del proyecto. Lo que tenemos es Web Forms.

ASP.NET MVC "de verdad"Lo que usamos nosotros
Ruta → Controller → Action → ViewURL → archivo .aspx físico
ActionResult, return View(model)Postback + ViewState
Razor (.cshtml).aspx / .ascx con controles de servidor
Controller = punto de entrada HTTPController = capa de acceso a datos
La idea clave En este proyecto "Controller" no significa "controlador HTTP". Significa la clase que habla con la base de datos. Es un repositorio disfrazado de controller.

Regla de oro — es la que más se rompe Cada capa habla solo con la de abajo. Una página nunca abre un SqlConnection. Un .ascx.cs nunca escribe SELECT. Un Controller nunca sabe que existe un RadGrid2. Un SP nunca sabe quién lo llamó.

El Model no es una capa: es el sobre en el que viajan los datos. Cruza todas.

03El Model

Archivo: 02-Ejemplo-Usuario/App_Code/MVC/Sigma/Model/Usuario.cs

Una clase POCO. Propiedades y nada más: cero métodos, cero validaciones, cero lógica.

[Serializable]
public class Usuario
{
    // Columnas reales: nombre = columna EN MINÚSCULAS con prefijo de tabla
    public int    usu_id      { get; set; }   // ← USU_ID
    public string usu_nombres { get; set; }   // ← USU_NOMBRES
    public int    usu_perfil  { get; set; }   // ← USU_PERFIL
    public bool   usu_habilitado { get; set; }

    // Campos del JOIN: para mostrar el nombre en vez del id
    public string per_nombre { get; set; }
    public string pai_nombre { get; set; }

    // Campos de FILTRO: NO existen en la base de datos
    public string filtro            { get; set; }
    public bool?  filtro_habilitado { get; set; }
    public int?   filtro_perfil     { get; set; }
    public string filtro_paises     { get; set; }
}

Las 4 reglas

  1. [Serializable] — el objeto viaja en ViewState y Session.
  2. Nombre de propiedad = nombre de columna en minúsculas. Sin PascalCase, sin nombres "bonitos".
  3. Prefijo de 3 letras de la tabla. USUARIO → usu_.
  4. Los filtro_* no existen en la BD. Solo los lee el Controller.
La pregunta que siempre sale: ¿por qué bool? y no bool? Con bool solo tienes dos estados. Con bool? tienes tres:
null → no filtrar, traer todos  ·  true → solo habilitados  ·  false → solo deshabilitados
Sin el ? sería imposible expresar "traer todos".

05Base de datos — nomenclatura

Guía completa: 01-Guias/GUIA_04_PATRON_SP.md

Regla de oro Nada de SQL en C#. Todo el acceso a datos pasa por un Stored Procedure.

Tres razones: seguridad (parámetros tipados, sin concatenación del usuario), mantenimiento (cambiar una consulta = ejecutar un script, sin recompilar) y trazabilidad (todo en un solo lugar auditable).

Contrapunto honesto — alguien lo va a plantear en el CAPSTONE Este patrón tiene costos reales: la lógica queda partida entre dos repositorios, es más difícil de testear unitariamente, y hoy la industria se movió bastante hacia ORMs (Entity Framework, Dapper). Es una arquitectura de los 2000s que sigue siendo válida en sistemas empresariales grandes con equipos de BD dedicados — que es el caso de FacilityGes. Para SIGMA lo adoptamos por consistencia con lo que el equipo ya sabe.
Prefijo SPAcción
SEL_Consulta (listado y get by id)
INS_Inserción
UPD_Actualización
DEL_Eliminación física
API_ / FNC_SP de API / funciones

Columnas: prefijo de 3 letras

USUARIO → USU_ID, USU_NOMBRES · PERFIL → PER_ID · PAISES → PAI_ID

En SQL MAYÚSCULAS, en el Model C# minúsculas. Es la única transformación de nombres del sistema.

Por qué el prefijo: en un SELECT con tres JOIN, USU_NOMBRES te dice de inmediato de qué tabla viene.

Auditoría — en toda tabla, sin excepción

USU_USUARIO_CREACION  INT
USU_FECHA_CREACION    DATETIME
USU_USUARIO_ACT       INT
USU_FECHA_ACT         DATETIME
USU_HABILITADO        BIT       -- baja lógica
Decisión para SIGMA En FacilityGes conviven _ACT y _ACTUALIZACION. Para SIGMA elegimos _ACT y lo usamos siempre. Definirlo ahora evita el desorden después.

06SEL_ — la query dinámica

El patrón más particular del proyecto: tres variables y un solo EXEC.

--SELECT
BEGIN
   DECLARE @SELECT VARCHAR(MAX)
   SET @SELECT = 'SELECT DISTINCT USU_ID, USU_RUT, USU_NOMBRES, PER_NOMBRE '
END

--FROM
BEGIN
   DECLARE @FROM VARCHAR(MAX)
   SET @FROM = ' FROM USUARIO
                 INNER JOIN PERFIL ON USU_PERFIL = PER_ID '
END

--WHERE
BEGIN
   DECLARE @WHERE VARCHAR(MAX)
   SET @WHERE = ' WHERE 1=1 '

   IF (@ID IS NOT NULL) BEGIN
       SET @WHERE = @WHERE + ' AND USU_ID = ' + LTRIM(@ID)
   END

   IF (@FILTRO IS NOT NULL) BEGIN
       SET @WHERE = @WHERE + ' AND (USU_NOMBRES LIKE ''%' + LTRIM(@FILTRO) + '%'')'
   END
END

--print(@SELECT + @FROM + @WHERE)
EXEC(@SELECT + @FROM + @WHERE)
El truco del WHERE 1=1 1=1 es siempre verdadero, así que no cambia el resultado. Su función es puramente sintáctica: permite concatenar AND ... sin preguntar nunca "¿es el primer filtro?". Sin él tendrías que llevar una bandera y decidir entre WHERE y AND en cada bloque.

El contrato C# ↔ SQL — enseñar con los dos archivos abiertos

// UsuarioController.cs
if (!string.IsNullOrEmpty(usuario.filtro))
    cmd.Parameters.AddWithValue("@FILTRO", usuario.filtro);
-- SEL_USUARIO.sql
@FILTRO VARCHAR(MAX) = NULL      -- ← el "= NULL" es imprescindible
...
IF (@FILTRO IS NOT NULL) BEGIN
    SET @WHERE = @WHERE + ' AND (...)'
END
Por eso todos los filtros llevan = NULL Si a uno se le olvida el = NULL y el C# no lo manda, el SP falla con "Procedure expects parameter which was not supplied".
Comillas dentro de comillas En T-SQL, dentro de un string una comilla simple se escribe doblada: ''. Como construimos SQL dentro de un string, hay que doblarlas. Se lee horrible; es el precio de la query dinámica.
La herramienta de depuración del patrón El --print(@SELECT + @FROM + @WHERE) se deja siempre comentado. Cuando algo falla: descomentas el print, comentas el EXEC, y ves la query armada tal cual.

07INS_ — insertar y devolver el id

CREATE OR ALTER PROCEDURE [dbo].[INS_USUARIO]
    @ID INT = NULL OUTPUT,      -- SIEMPRE primero
    @EMAIL NVARCHAR(200),
    @USUARIO INT                -- SIEMPRE último
AS
SET NOCOUNT ON

-- 1. Validaciones FUERA de la transacción
BEGIN
    IF EXISTS (SELECT 1 FROM USUARIO WHERE USU_EMAIL = @EMAIL)
    BEGIN
        RAISERROR('1.- Ya existe un usuario con el email "%s".', 16, 1, @EMAIL)
        RETURN -1
    END
END

-- 2. Transacción
BEGIN TRANSACTION
    INSERT USUARIO (...) VALUES (...)
    SET @ID = SCOPE_IDENTITY()

    IF @@ROWCOUNT = 0 BEGIN
        ROLLBACK TRANSACTION
        EXEC INS_EXCEPCION @MSG = '3.- NO FUE POSIBLE INSERTAR EL USUARIO.',
                           @VARIABLES = @VARIABLES
        RETURN -1
    END
COMMIT TRANSACTION

RETURN(0)
¿Por qué SCOPE_IDENTITY() y no @@IDENTITY? @@IDENTITY devuelve el último identity de la sesión, incluyendo los que generen los triggers. Si mañana alguien agrega un trigger de auditoría a USUARIO, te devolvería el id de la tabla de log en vez del usuario. SCOPE_IDENTITY() se limita al ámbito actual. Es un bug real y difícil de encontrar.

RAISERROR — anatomía

RAISERROR('1.- Ya existe un usuario con el email "%s".', 16, 1, @EMAIL)
--          └── mensaje con %s        severidad ─┘  │   └── valor de %s
--                                            estado ┘
  • %s es un marcador de sustitución, como String.Format.
  • 16 = severidad "error corregible por el usuario". Es la que hace que .NET lance SqlException.
  • Los mensajes se numeran (1.-, 2.-) para identificar qué validación falló.
INS_EXCEPCION Escribe en una tabla de log. La regla de @VARIABLES: tiene que permitir reproducir la llamada. Si el log dice solo "no se pudo insertar", no sirve de nada.

08UPD_ — el truco de ISNULL

UPDATE  USUARIO
SET      USU_RUT         = ISNULL(@RUT,      USU_RUT)
        ,USU_NOMBRES     = ISNULL(@NOMBRES,  USU_NOMBRES)
        ,USU_PASSWORD    = ISNULL(@PASSWORD, USU_PASSWORD)
        ,USU_HABILITADO  = ISNULL(@HABILITADO, USU_HABILITADO)
        ,USU_USUARIO_ACT = @USUARIO
        ,USU_FECHA_ACT   = GETDATE()
WHERE   USU_ID = @ID

ISNULL(@PARAM, columna_actual) = "si me mandaron el parámetro, úsalo; si no, deja el valor que ya tenía".

Esto habilita updates parciales con un solo SP El botón "Deshabilitar" del grid manda solo @ID, @HABILITADO y @USUARIO — el resto queda intacto. No hace falta un UPD_USUARIO_HABILITADO aparte.

El caso más elegante: la contraseña

// Solo se manda si el usuario escribió una nueva
if (!string.IsNullOrEmpty(usuario.usu_password))
    cmdExecute.Parameters.AddWithValue("@PASSWORD", usuario.usu_password);

Sin ISNULL habría que traer la contraseña actual, mandarla de vuelta y guardarla otra vez — con el riesgo de exponerla en el camino.

La validación de unicidad cambia en el UPDATE 
IF EXISTS (SELECT 1 FROM USUARIO WHERE USU_EMAIL = @EMAIL AND USU_ID <> @ID)
El AND USU_ID <> @ID es imprescindible: al editar sin cambiar el email, el propio registro haría match y el SP diría "ya existe". Se excluye a sí mismo.

DEL_ — el que casi no se usa

Tipo de tablaBaja
Maestro (USUARIO, PERFIL, CLIENTE)Lógica: UPD_ con HABILITADO = 0
Detalle / relación (USUARIO_INSTALACION)Física: DEL_

Por eso el UsuarioController expone DeshabilitarUsuario() y es ése el que llama el botón del grid — no DeleteUsuario().

12Combos y validación

El patrón LoadControls

Varios combos apuntan al mismo método, que se desambigua con un switch:

public void LoadControls(object sender, EventArgs e)
{
    if (!IsPostBack)                       // ① sin esto, pierde la selección
    {
        if (sender is RadComboBox2)
        {
            RadComboBox2 ctrl = (RadComboBox2)sender;
            switch (ctrl.ID)
            {
                case "cboPerfil":
                    ctrl.Items.Add(new RadComboBoxItem("Seleccione...", ""));
                    ctrl.AppendDataBoundItems = true;      // ② sin esto, se borra el item
                    ctrl.DataSource = new PerfilController().GetPerfiles(filtro);
                    ctrl.DataValueField = "per_id";        // ③ nombres del MODEL
                    ctrl.DataTextField  = "per_nombre";
                    ctrl.DataBind();
                    break;
            }
        }
    }
}
  1. if (!IsPostBack) — síntoma si falta: "escojo un perfil, guardo, y el combo vuelve a Seleccione".
  2. AppendDataBoundItems = true — sin esto, DataBind() borra el item "Seleccione...".
  3. DataValueField/DataTextField son propiedades del Model. Un typo falla en runtime, no al compilar.

Para seleccionar se usa cboPerfil.SelectedValue = "3" (el Value), nunca el Text.

<WebControls:TextBox2 ID="txtEmail" runat="server" MaxLength="200" />

El bug más frustrante de esta capa Si el ValidationGroup no coincide, los validators no se ejecutan y el formulario guarda vacío. No hay error ni warning: falla en silencio.

Sin ella, el botón Guardar dentro de un UpdatePanel no dispara postback. Síntoma: "hago click en Guardar y no pasa absolutamente nada".

13ItemCreated vs ItemDataBound

Guía completa: 01-Guias/GUIA_03_PATRON_GRID_EVENTS.md

Anunciarlo de entrada En este proyecto NO usamos OnItemCommand del grid. Es la forma "de manual" de Telerik, la que aparece en toda la documentación oficial, y aquí no se usa. Hay que decirlo explícitamente: el equipo va a buscar en Google, va a encontrar ItemCommand, y va a introducir un patrón que no calza con el resto del código.

¿Por qué hacen falta DOS eventos y no uno?

La pregunta que siempre aparece. La respuesta está en el ciclo de vida:

La clave Para que un control dinámico dispare su evento después de un postback, tiene que haber sido creado antes de que ASP.NET procese el postback. ItemDataBound corre demasiado tarde: si creas el LinkButton ahí, se ve pero al hacer click no pasa nada. 
protected void Grid_ItemCreated(object sender, GridItemEventArgs e)
{
    if (e.Item is GridDataItem)
    {
        GridDataItem item = (e.Item as GridDataItem);

        lnkDescarga.ID = "lnkDescarga";        // ① ID FIJO en todas las filas

  2. La suscripción Command += va AQUÍ, no en ItemDataBound.
  3. RegisterPostBackControl es obligatorio dentro de un UpdatePanel.
  4. La columna tiene que existir: se crea con AddTemplateColumn en Page_Load.

15Las 10 reglas del patrón

  1. No es ASP.NET MVC. Es WebForms; "Controller" = capa de acceso a datos.
  2. Cada capa habla solo con la de abajo. .aspx → .ascx → Controller → SP → tabla.
  3. El Model es solo datos. POCO [Serializable], propiedades <pfx>_<columna> en minúsculas. Los filtro_* no existen en la BD.
  4. Cero SQL en C#. Todo pasa por SEL_ / INS_ / UPD_ / DEL_.
  5. Token.TokenSeguridad() abre todo método del Controller.
  6. Los parámetros de filtro se agregan solo si vienen informados. Es el contrato con el WHERE 1=1.
  7. Se carga en Page_PreRender, se guarda en el evento del botón.
  8. Las propiedades públicas de un UserControl van en ViewState, nunca en campos privados.
  9. Toda escritura devuelve Respuesta (codigo, detalle, error), y ese detalle llega al usuario final.
  10. UTF-8 con BOM y CRLF en todos los .cs, .ascx, .aspx y .sql.
El punto 10 no es cosmético Si el archivo se guarda en UTF-8 sin BOM, las tildes y las ñ se rompen al compilar en el servidor.
